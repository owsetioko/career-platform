# Ex05: Investigate a DNS or TLS Failure

**Simulation** — deliberate lab failure using supplied output.
Hostnames, IPs, and commands are invented for this exercise.

---

## 1. Setting and Prediction

This is the supplied simulation. The check being tested is a `curl -Iv`
request to `https://site.lab.example/`. My prediction is that it fails
with a TLS error because the DNS A record still points to an old Azure
VM, and that VM's certificate was issued for a different hostname — so
even if the connection goes through, TLS will reject it.

---

## 2. Failed Check and Evidence

**Simulated output:**

```text
$ dig site.lab.example A +noall +answer
site.lab.example. 300 IN A 198.51.100.24

$ curl -Iv https://site.lab.example/

Connected to site.lab.example (198.51.100.24) port 443
Server certificate: subject: CN=old-vm.lab.example
SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

The `dig` shows the domain resolving to `198.51.100.24`, which is the
old Azure VM. When `curl` connects to that IP, the certificate it gets
back says `CN=old-vm.lab.example` — a completely different name — so
TLS fails right there.

---

## 3. Diagnosis

DNS sent traffic to the old Azure VM at `198.51.100.24` instead of
Railway. That VM's certificate was issued for `old-vm.lab.example`,
not `site.lab.example`, so TLS rejected it. DNS was the first fault —
the TLS error followed from it. Whether Railway's app is actually
healthy is still unknown since we never reached it.

---

## 4. Repair and Repeated Check

Delete the old A record in Cloudflare and add a CNAME pointing
`site.lab.example` to `current-app.up.railway.app`. A repeated `dig`
would then show the CNAME instead of the old IP, and `curl` would
reach Railway's server with a valid certificate and return HTTP 200.
I interpreted the supplied follow-up output rather than running it
myself — it confirmed my initial diagnosis.

---

## 5. What I Learned

To separate a DNS problem from a TLS problem, bypass the broken DNS
record and send the request straight to Railway, while still asking
for `site.lab.example`:

```bash
curl -Iv --connect-to site.lab.example:443:current-app.up.railway.app:443 https://site.lab.example/
```

If TLS succeeds, Railway's certificate is fine and DNS was just
pointing to the wrong place. If TLS still fails, Railway's certificate
for the custom domain is also a problem. If the failure
continued after the DNS fix, I would check whether Railway issued a
certificate for the custom domain and whether the TXT record verified.
